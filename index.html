Ray 原生沙箱

把"创建一个隔离环境"变成和"创建一个 Actor"一样普通. 以前要搭沙箱服务, 现在一行 sandbox.create() 就行.

2026·10·21 · 原文 ↗ · Philipp Moritz · Andrew Sy Kim · Xinyu Zhang
核心一句话

Ray 2.58 起, 沙箱 = 一个 Ray Actor + 一个 gVisor 环境. Ray 管编排扩缩, gVisor 管隔离. 不再需要独立的沙箱控制面.

PART 01先理解场景: 为啥需要海量沙箱

Agentic RL 一次训练的样子

一个 batch: 模型生成 1000 份代码 (每份都想"解决"同一道题) ↓ 这 1000 份代码并发跑, 看哪个过测试 ↓ 跑过的 → 正样本, 没过的 → 负样本 ↓ 用样本更新模型

关键: 这 1000 份代码得真跑一遍. 不能在训练节点上直接 exec, 因为:

  • 代码是模型瞎编的, 可能 rm -rf /
  • 可能跑死循环把节点吃爆
  • 可能写一堆文件污染环境

所以每份代码必须有自己的隔离环境, 跑完销毁. 一次 batch 要 1000 个环境, 一天几千 batch = 几百万次创建销毁. 这就是"海量沙箱"的来源.

PART 02关键洞察: 沙箱就是 Actor

把两边的能力清单摆一起:

Ray Actor 本来就有沙箱需要的
调度到某台机器上调度到某台机器上 ✓
分配 CPU / mem分配 CPU / mem ✓
挂了自动重建挂了自动重建 ✓
用完销毁用完销毁 ✓
大规模并行创建大规模并行创建 ✓

一模一样. Anyscale 的想法: 别再写一套, 直接让 Actor 身上多一个 gVisor 隔离层 就行.

PART 03gVisor 到底是啥

把它想成 "假装自己是 Linux 内核的用户态程序".

syscall 路径对比

普通 Docker
容器 python
  open("/etc/passwd")
    ↓
宿主 Linux kernel
  真实 sys_open

内核漏洞被触发
= 容器逃逸
= 拿到宿主
gVisor (runsc)
容器 python
  open("/etc/passwd")
    ↓ 拦截
gVisor Sentry
  用户态模拟 open
    ↓ 需要时才问
宿主 kernel (小 syscall)

逃逸要攻破两道门
好处

容器里恶意代码接触不到真正 kernel. 要逃出去得先攻破 Sentry (用户态程序, 攻击面小几十倍), 再攻破 kernel.

代价

多一层转译, syscall 慢 10-30%. 对 Agent 跑脚本不敏感.

OCI 兼容

Docker 镜像拿过来就能用, 不用改. runtime 从 runc 换成 runsc 即可.

四种隔离方案横向比

方案隔离启动syscall 开销
Docker (runc)低, 共享 kernel~100ms0
gVisor (runsc)中, 用户态 kernel<1s中
Firecracker高, 微 VM125ms+低
Kata高, VM500ms+低

gVisor 的甜点: 隔离够强 + 启动够快 + OCI 生态.

PART 04API 两层: 为啥这么设计

高层 — 90% 的人用这个

from ray.experimental import sandbox

sb = sandbox.create(
    image="python:3.12-slim",   # 用啥镜像
    cpu=1.0, memory="512Mi",    # 要多少资源
    network="none",              # 要不要网
)
ray.get(sb.exec.remote("python -c '1+1'"))  # 跑命令
sb.delete.remote()                           # 用完销毁
关键细节

sb 是 Ray Actor handle. 这意味着:

  • sb 可能在集群任意一台机器上, 调用方不用管
  • sb.exec.remote(...) 走 Ray 的 RPC, 自动序列化参数
  • 多个 Actor 并发创建沙箱 = 自动并发创建, 不用自己写线程池

底层 — 想自己造沙箱服务的人

# 跑在某台机器上的 Actor, 自己管沙箱池
@ray.remote
class SandboxPool:
    def __init__(self):
        self.rt = SandboxRuntime()   # 直接拿本地 gVisor
        self.pool = {}

    def create(self, sid):
        self.pool[sid] = self.rt.create(image="...")

为啥要这层: 高层每个沙箱是一个 Actor, 创建有开销. batch 场景 1 秒要起 1000 个沙箱, 1 个 Actor 管 100 个沙箱更快. 这层给你这个控制.

OCI spec 回调 — 最硬核的能力

def harden(spec):
    # 这是即将传给 gVisor 的 OCI JSON spec, 你能改任何字段
    spec["process"]["rlimits"].append({
        "type": "RLIMIT_NPROC",
        "hard": 100, "soft": 100,   # 最多 100 个进程, 防 fork bomb
    })
    # 清所有 Linux capability
    spec["process"]["capabilities"] = {
        k: [] for k in (
            "bounding", "effective", "permitted",
            "inheritable", "ambient",
        )
    }
    return spec

sb = sandbox.create(image="...", _oci_spec_transform_fn=harden)

意义: 不用等 Ray 加参数, 你现在就能打补丁加任何 Linux 安全约束.

PART 05网络四模式 — 实战意义

模式实际场景
none跑 SWE-Bench. 模型生成的修复代码, 测试跑完就销毁, 不该联网
public装依赖. 代码里有 pip install requests, 得联网
host调诊断. 沙箱内脚本要访问宿主的 Prometheus/Loki
sandbox多 agent 协作. 两个沙箱间要通信 (如一个 agent 调另一个 agent 的 API)
默认 none 的意义

开发者忘了配网, 代码也跑不出去. 比默认开着网安全得多.

文件传输

  • 小文件 (配置/脚本): write_file / read_file 直接走 Ray object store
  • 大目录 (代码仓库/数据集): tar 打包传输, 保留权限、符号链接、空目录; 跨节点自动走 object store

PART 06规模数字的分量

"GKE 上 20 秒起 10 万沙箱" 拆开看:

100K
并发沙箱
20s
启动耗时
5K/s
总吞吐

假设 2000 节点, 每节点 2.5 沙箱/秒 的冷启.

同规模走 K8s pod

K8s API server 每秒能处理约 50-100 个 pod 创建. 10 万 pod 要 1000 秒 (16 分钟) + API server 直接压崩.

为啥 Ray 能快 50 倍

  1. 创建沙箱 = 创建 Actor = Ray worker 本地起个 gVisor 进程, 不走 API server
  2. 调度决策是 Ray scheduler 的 raylet 分布式做, 不是单点 kube-scheduler
  3. gVisor 本身比完整 pod 轻 (没 kubelet / CNI / CSI 这堆)

  • 单 trial 29s — 包含 gVisor 启动 + agent 跑题 + 测试执行

轻量级 agent 评测这类负载, Ray Sandbox 已经可用于生产.

PART 08六个坑: 现在不能干啥

坑影响
experimentalAPI 下个版本可能改, 别锁死
无 GPU 沙箱要跑 CUDA kernel generation 的 RL, 用不了
内嵌 Docker 未测需要在沙箱里再起容器的 (如 CI 场景) 没保障
无 FS 快照批量从同一 base 分叉 (如 1000 个变体共享 base layer) 做不到
无端口暴露沙箱里跑个 web server 让外面访问? 做不到
必须依赖 Ray想独立做个 sandbox-as-a-service 用不了
结论

当前只适合"CPU + 代码执行 + 短生命周期"场景.

PART 09我的判断 — 价值在哪

不是"又一个沙箱". 价值在消除第二套控制面.

对比两种世界

世界 A: 现有

训练集群 (K8s + Ray) + 独立沙箱系统 (另一套 K8s? E2B? 自建?)

  • 两套调度打架
  • 两套资源账本
  • 两套扩缩逻辑
  • 两个 oncall
世界 B: Ray Sandbox

训练集群和沙箱 同一套 Ray

  • 一个 autoscaler 看全局负载
  • 一个资源账本
  • 一套扩缩逻辑
  • 一个 oncall
杀手锏

运维简化是真正杀手锏. 性能是副产品.

攻击面也要注意

  • CVE-2023-3978 (DNS 解析) 等 gVisor 历史漏洞存在
  • 共享 host, 侧信道 (Spectre 等) 仍适用
  • 原文明说 "future: guidance for models actively trying to escape"
  • → 官方承认当前防御未针对主动攻击者优化

PART 10落地的两个关键判断

判断 1

你的 workload 需要 GPU 沙箱吗?

  • 要 → 等几个版本
  • 不要 (纯 CPU 代码执行) → 可以试
判断 2

你的 workload 需要联网服务吗?

  • 要 (agent 调外部 MCP server, 沙箱间通信) → 看端口暴露/快照路线图
  • 不要 (封闭环境跑完就销毁) → 可以试

对 ray-agent (我们项目) 的具体答案

  • 当前: 只读诊断, 完全不涉及, 不用动
  • 未来: 要做"自愈动作执行" (如 patch 配置后 dry-run), 这就是比 kubectl exec 安全得多的落点
  • 短期: 继续读 Ray release notes, 等 REST API 版本 (PR #65633) 出来

国内落地建议

  • Ray 2.58 实验性, 生产用观察几个版本
  • 节点需预装 runsc, 基础镜像自己打
  • 国内 GKE 不可用, 自建 K8s + Ray Autoscaler 也能跑
  • 关键看沙箱放置能否复用现有调度策略
