把沙箱做成 Ray 一等公民, 消除 RL 后训练场景中的第二套控制面. 来自 RL 用户的使用反馈 + 对 Ray 团队的功能请求.

PART 01RL 与后训练: 场景定位

RL 后训练在近年快速演进, 本节先对齐术语和场景, 为后续讨论建立基础.

后训练四种玩法

玩法训练方式数据/反馈来源
SFT (监督微调)人工标注指令-回答样本, 直接训练静态标注数据集
DPO (偏好对齐)(优选, 劣选) 样本对训练, 依赖 Reference Model静态偏好数据集
RLHF / GRPO模型自主生成 trajectory, 奖励打分形成完整训练闭环在线采样 + 文本层奖励
Agentic RL多轮调用工具 / 生成代码, 沙箱执行获取真实反馈外部环境执行结果
关键区分
  • SFT / DPO: 数据是预先准备好的静态数据集, 无在线环境交互
  • RLHF / GRPO: 在线采样 trajectory, 但奖励大多是文本层面打分 (reward model 评分)
  • Agentic RL: 奖励来自外部环境执行结果 (代码在沙箱里跑出的输出), 属于交互式强化学习, 必须沙箱

GRPO 是 RLHF 的轻量化变体 — 模型自己生成多条 trajectory, 组内对比得到奖励, 不需要单独训练 reward model.

Ray 对 SFT/DPO 用处有限 (就是 FSDP 包一下). 真用武之地在 RLHF 和 Agentic RL, 因为要同时跑三类负载:

角色资源工作
Trainer大 GPU算梯度, FSDP / Megatron
RolloutGPU模型推理, 生成 trajectory
Env纯 CPU跑环境, 返回 reward

Agentic RL 跟传统 RL 的本质差别

传统 RL (Atari / Mujoco)
  • Env = 进程内 Python 对象
  • step() 就完事
  • 可信, 不需要隔离
  • 单轮决策
Agentic RL (SWE-Bench 等)
  • Env = shell / 代码执行器
  • 模型输出代码, env 跑, 返 stdout+exit_code
  • 不可信, 必须隔离
  • 多轮 (ReAct), 跨步状态保持

一次 Agentic RL batch 的量化

batch_size = 1024 prompts samples_per_prompt = 8 avg_turns_per_episode = 10 (ReAct 多轮) → 单 batch sandbox exec = 1024 × 8 × 10 = 81,920 次 → 单 batch 并发 sandbox = 8,192 个 (每 episode 一个) → 一天几千 batch → 一次完整训练 = 几千万次 sandbox 创建+exec+销毁

这个数量级是后面"10 万沙箱 benchmark"的锚点. 不是 Anyscale 吹数字, 是 RL 真需要.

主流后训练框架都是 Ray 底座

  • veRL (字节, 最成熟)
  • NeMo-RL (NVIDIA)
  • SkyRL (UC Berkeley + Anyscale, Agentic 最激进)
  • SLIME / MILES (研究用)

→ 已经是**事实标准**. Ray Sandbox 不是来抢占新市场, 是补**已有用户群**的最后一块.

PART 02沙箱技术: gVisor 与 Docker 对比

沙箱的定义

一个一次性的、强隔离的 Linux 环境, 用来跑不可信代码. 跑完销毁. 要求:

  • 模型里 rm -rf / 不会伤到宿主
  • fork bomb 不会打死节点
  • 读不到宿主秘钥 / 其他沙箱数据
  • 启动够快 (百毫秒级)

gVisor 是啥

Google 2018 开源的 用户态 Linux 内核, Go 写的. OCI 兼容, 可执行名 runsc, 跟 runc 同级.

和 Docker 的 syscall 路径对比

Docker (runc)
容器里 python
  open("/etc/passwd")
    ↓
宿主 Linux kernel
  真实 sys_open

内核漏洞被触发
= 容器逃逸
= 拿到宿主
gVisor (runsc)
容器里 python
  open("/etc/passwd")
    ↓ 拦截
gVisor Sentry
  用户态模拟 open
    ↓ 需要时才问
宿主 kernel (小 syscall)

逃逸要攻破两道门

隔离方案横向比

方案隔离启动syscall 开销
Docker (runc)低 · 共享 kernel~100ms0
gVisor (runsc)中 · 用户态 kernel<1s中 (10-30%)
Firecracker高 · 微 VM125ms+低
Kata高 · VM500ms+低
为啥 Ray 选 gVisor

Agentic RL 要的是 隔离够强 + 启动够快 + OCI 生态. gVisor 刚好是这三者交集的甜点. Firecracker 隔离更强但启动慢 2-3 倍, 10 万并发不划算.

PART 03核心痛点: 架构, 而非性能

一次典型 Agentic RL 训练需要几千万次沙箱执行. 老方案有两条路:

老路 A: 自建 Docker
  • 共享 kernel → 模型触发 CVE 容器逃逸
  • 要挂 docker socket → 等于交出宿主
  • runc 启动 ~100ms, 10 万要 1000s
  • dockerd 跟 Ray 分治, 不协调
老路 B: 独立沙箱服务 (E2B / Sandbox Fusion)
  • 跨集群 HTTP RPC, 延迟放大
  • 两套 autoscaler → 协调不了
  • 两套资源账本 → GPU/CPU 不能统一预算
  • 两个 oncall
核心痛点

两条路同一个病: 两套控制面. Ray 看不到沙箱的资源占用, autoscaler 无法协调 rollout 扩容和 sandbox 扩容的节奏. 这是架构级错误, 优化改不动.

Ray handles orchestration and scaling. gVisor handles isolation.
— 原博文, 2026-08-25

这不是性能宣言, 是职责边界宣言. 两套控制面合并成一套, 才是重点.

Ray Sandbox 的真正价值不是跑得多快,
是让 RL 框架能把沙箱当 Actor 用.
消除第二套控制面.

PART 04核心架构: Sandbox = Actor + gVisor

一句话定义

一个 Sandbox = 一个 Ray Actor + 一个 gVisor 环境. 不引入新抽象.

它在 Ray 生态里的位置

Ray Core (Actor / Task / Object Store / PG) ├─ Ray Train ← 分布式训练 (FSDP / Megatron) ├─ Ray Serve ← 推理服务 ├─ Ray Data ← 数据加载 ├─ Ray Tune ← 超参搜索 └─ Ray Sandbox ✨ ← 不可信代码执行 (基于 Actor + gVisor)

Ray Sandbox 是 Ray Core 之上的第 5 个 library. 它复用 Core 的全部原语, 不是新造一套.

创建一个沙箱, Ray 内部发生啥

用户: sandbox.create(image="python:3.12-slim", cpu=1.0, memory="512Mi") │ ↓ Ray Scheduler (raylet) ├─ 选节点 (按资源余量 + 亲和性) ├─ 预留 CPU=1.0, mem=512Mi └─ 分配 bundle (如在 PG 下) │ ↓ 节点上拉起 Proxy Actor (Python 进程) │ ↓ Proxy Actor 调 runsc (gVisor OCI runtime) │ ↓ gVisor 起 Sentry 用户态内核 + 容器进程 │ ↓ 返回 Actor handle → 用户

两层 API

高层 · 90% 场景
sb = sandbox.create(
    image="python:3.12-slim",
    cpu=1.0, memory="512Mi",
    network="none",
)
result = ray.get(
    sb.exec.remote("python script.py")
)
sb.delete.remote()

sb 是 Ray Actor handle, 自带 Ray 全部能力

底层 · 自建沙箱池
@ray.remote
class SandboxPool:
    def __init__(self):
        self.rt = SandboxRuntime()
        self.pool = {}

    def create(self, sid, spec):
        self.pool[sid] = self.rt.create(spec)

直接拿本地 gVisor, 可修改 OCI spec

关键能力: OCI spec 回调

这是 Ray Sandbox 最硬核的扩展点. Ray 不急着把每种安全约束做成 API, 而是开了个 escape hatch:

def harden(spec):
    # 防 fork bomb
    spec["process"]["rlimits"].append({
        "type": "RLIMIT_NPROC", "hard": 100, "soft": 100,
    })
    # 清所有 Linux capability
    spec["process"]["capabilities"] = {
        k: [] for k in ("bounding", "effective", "permitted",
                        "inheritable", "ambient")
    }
    return spec

sb = sandbox.create(image="...", _oci_spec_transform_fn=harden)

用户不等 Ray 发版加参数, 自己改 OCI spec 就能加任意 Linux 安全约束. 对 Ray 团队的意义: feature backlog 压力小一个量级.

PART 05Actor 映射: 沙箱如何复用 Actor 原语

Sandbox 复用 Actor 已有能力的对照关系:

Actor 原生能力Sandbox 怎么用
@ray.remote 创建sandbox.create(...) 内部就是建 Actor
Actor handlesb 对象 — 跟普通 handle 一样可以传、可以在远端调方法
actor.method.remote()sb.exec.remote(cmd) — 普通 Ray RPC
Resource request (num_cpus / num_gpus)sandbox.create(cpu=1.0, memory="512Mi") 转成 Actor 的 options

max_restarts 故障恢复Actor 挂了 → Ray 自动重建 → 沙箱重建, 不用用户写重试
AutoscalerN 个 sandbox pending → Ray 扩节点
Lifecycle (ray.kill)sb.delete.remote() 内部清 gVisor + 杀 Actor

两层 class 关系

用户视角 Ray 层 OS 层 ───────── ────── ───── sandbox.create(...) ↓ ↓ Proxy Actor (Python) ↓ │ ↓ │ subprocess.Popen ↓ ↓ ↓ runsc (gVisor OCI runtime) ↓ │ ↓ │ clone + ptrace ↓ ↓ Sentry (用户态 kernel) │ ↓ 容器进程 (真正跑代码) sb (Actor handle) │ ↓ sb.exec.remote(cmd) │ Ray RPC ↓ Proxy Actor . exec(cmd) │ ↓ runsc exec ↓ 容器内跑 cmd, 返回 stdout/stderr/exit_code

关键细节: Proxy Actor 做啥

Proxy Actor 是普通 Python Actor, 本身**不是**沙箱, 只是沙箱的 Ray 代理. 它:

  • 持有一个 gVisor 容器实例 (子进程)
  • 把 Ray RPC 翻译成 runsc 调用
  • 管理容器生命周期
  • 生命周期跟容器绑死 — Actor die → 容器清理

这个设计让 Sandbox 不需要新调度器 — Proxy Actor 的放置就是沙箱的放置, Ray scheduler 已经做得很好.

一个端到端例子: Agentic RL rollout worker

@ray.remote(num_gpus=1)
class RolloutWorker:
    def __init__(self, model_ref):
        self.model = load(model_ref)

    def rollout(self, task):
        # 创建 sandbox = 创建另一个 Ray Actor
        sb = sandbox.create(
            image=task.image, network="none",
            cpu=1.0, memory="1Gi",
        )
        try:
            state = ray.get(sb.exec.remote(task.setup)).stdout
            trajectory = []
            for step in range(task.max_steps):
                action = self.model.generate(state)
                if action.has_tool_call:
                    # Ray RPC: 跨节点都没问题
                    result = ray.get(sb.exec.remote(action.code))
                    trajectory.append((state, action, result))
                    state = result.stdout
                else:
                    break
            return trajectory
        finally:
            sb.delete.remote()  # 用后即焚

关键: RolloutWorker 和 Sandbox 很可能在不同节点 (GPU 节点 vs CPU 节点). sb.exec.remote() 自动走 Ray RPC, 用户不用关心跨节点传输. Ray 把分布式复杂度完全藏住.

对标 K8s

路径创建速率10 万沙箱耗时
K8s pod (走 API server)50-100/秒~1000s = 16 min, API server 大概率压崩
Ray Sandbox5000/秒20s
快 50 倍的原因

不是 gVisor 本身快, 是 Ray 调度器的工程威力:

  1. 创建不走 API server, raylet 本地拉起
  2. 调度决策分布式, 每个 raylet 独立判断, 非单点
  3. Actor 比 pod 轻 (没 kubelet / CNI / CSI 全家桶)
  4. gVisor 启动比完整容器栈省几个步骤

这段讲给 Ray 团队, 他们会会心一笑 — 这些是他们已经把 Ray Core 做好的能力, 只是被 Sandbox 顺势复用了.

这个数字对 RL 的意义

回到 Part 2 的 batch 量化:

  • 一个 batch 需要 ~8 万次 sandbox exec
  • Ray Sandbox 5000/s 吞吐 → 创建时间 16 秒 ≪ episode 执行时间 (分钟级)
  • → 沙箱创建开销可忽略

换句话说, Ray Sandbox 的性能不是"刚好够用", 是把这个变量从 RL 系统架构里消去了. RL 用户不用再把沙箱启动延迟当设计约束.

PART 07实战能力: 网络模式与 OCI 回调

网络 4 模式: 架构级安全默认

模式行为典型用途
none (默认)仅 loopbackSWE-Bench 不可信代码
public允许出公网pip install, 调外部 API
host共享节点 netns访问宿主服务
sandbox独立网络栈多 agent 协作
设计亮点

默认 none 是对的. 开发者忘记配网, 代码就跑不出去; 比默认开着网 (K8s pod 的默认) 安全好几个数量级. 这是 Ray 团队给整个生态树的样板.

OCI spec 回调: 技术威力

前面讲过, 不重复. 补一个 Ray 团队视角:

  • 每个 Linux 安全特性都做 Python 参数 → feature creep
  • 只开一个 OCI spec 回调 → 用户社区自己写加固模板
  • Ray 团队维护成本小一个量级

其他能力 (文件传输 / MCP 后端) 一笔带过 — 都是 API 便利, 不是架构创新.

veRL (Volcengine 字节) — 待集成

veRL 当前用 Sandbox Fusion — Volcengine 自家的 HTTP code sandbox 服务. 架构:

veRL Agent Loop ↓ BaseTool.execute(code) ↓ HTTP POST → Sandbox Fusion 服务 (独立集群) ↓ 返回 stdout / exit_code

切换到 Ray Sandbox 的路径非常清晰:

# 当前
class CodeTool(BaseTool):
    def execute(self, code):
        resp = requests.post(sandbox_fusion_url, json={"code": code})
        return resp.json()

# 切换后
class CodeTool(BaseTool):
    def __init__(self):
        self.sb = sandbox.create(image="python:3.12-slim", network="none")
    def execute(self, code):
        return ray.get(self.sb.exec.remote(code))
集成成本

一个 class 改两行. 不动框架骨架, 不动 trainer, 不动 rollout. 这是 Ray Sandbox 架构设计的直接结果 — 对接是"替换一个 HTTP client"级别.

PART 09RL 用户反馈与功能请求

本节总结生产落地中遇到的阻塞, 以及对 Ray 团队的功能请求.

当前阻塞生产的四个硬门槛

门槛影响优先级
REST API 版本 (PR #65633)训练集群和沙箱集群物理分离. 内网训练集群跑不可信代码, 安全团队不会批. 这是落地的最低门槛P0
GPU sandboxCUDA kernel generation / RSI 场景需要. 普通 Agentic RL 不急 (推理在 rollout actor)P1
跨 sandbox 端口暴露Multi-agent 协作 (agent A 调 agent B 的 web server) 做不到P1
文件系统快照1000 变体从同一 base 分叉, 共享 layer. 现在每个冷启P2

Ray 调度能力的具体改进请求

这些是 RL 框架用 Ray 时碰到的, 不限于 Sandbox:

  • 更细的 bundle 分数共享 — hybrid engine (train + rollout 同进程) 疯狂用 num_gpus=1/N. 希望这个机制有一等公民 API
  • AsyncActor context switch 延迟优化 — trainer ↔ rollout 切换是热路径, 几十 ms 的延迟累积很可观
  • NCCL + Ray 互操作 — collective group management 现在要框架自己写, 希望有标准接口

Agentic RL 真正的瓶颈 (供参考)

这个讲给 Ray 团队, 让他们知道沙箱不是最大瓶颈:

  1. Long-horizon trajectory 的权重同步频率 — 一个 episode 几十分钟, 要不要 off-policy? SkyRL 在用 async weight update 解
  2. Tool call 的异步调度 — ReAct 要并发工具调用, Ray asyncio 够不够顺手
  3. Replay buffer 的分布式存储 — 大 trajectory 存哪, object store 够不够

Sandbox 是基础设施收尾, 不是性能瓶颈. 但它决定框架能不能把沙箱当一等公民.

一句话收尾

Ray Sandbox 的真正价值不是跑得多快, 是让 RL 框架能把沙箱当 Actor 用.
下一步希望 Ray 团队把REST API + GPU sandbox + cross-sandbox port 补齐 —
这是我们 RL 落地的三个硬门槛.
