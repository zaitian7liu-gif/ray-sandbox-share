1 · 背景

要解决什么

Agentic RL / Coding Agent 后训练, 需并发跑模型生成的代码.

三个硬约束:

  • 不可信 — LLM 产出可能恶意/误操作, 要强隔离
  • 规模大 — 一次 RL rollout 几千~几万并发环境
  • 动态 — 启动快, 用完销毁, 不是长生命周期服务

现有方案痛点

方案问题
独立沙箱服务 (E2B / Modal)自带调度+控制面, 和训练集群两套系统
裸 Docker共享 kernel, 隔离不足以挡恶意代码
Firecracker启动 100ms+, 大规模短生命周期代价高
Ray handles orchestration and scaling.
gVisor handles isolation.

2 · gVisor 扫盲

  • Google 开源, 2018 年起
  • 用户态 Linux kernel, Go 写的
  • 应用 syscall → Sentry 进程拦截 → 用户态模拟或转发
  • 攻击面: 几百 syscall → 几十
  • OCI 兼容, runtime 名 runsc, 替换 runc
  • 代价: syscall 密集场景性能损失 10~30%

隔离方案对比

方案隔离启动syscall 开销
Docker (runc)低 (共享 kernel)~100ms0
gVisor (runsc)中 (用户态 kernel)<1s中
Firecracker高 (微 VM)125ms+低
Kata高 (VM)500ms+低

gVisor 甜点: 隔离够强 + 启动够快 + OCI 生态

核心映射

Ray 概念Sandbox 概念
一个 Actor一个沙箱
Actor 调度沙箱放置 (复用 placement group)
Actor 生命周期沙箱生命周期
Actor 故障恢复 (max_restarts)沙箱重建

好处: 不用自己写调度器 / 资源管理 / 控制面. Ray 当分布式 OS, 沙箱当"进程".

4 · API 两层设计

高层: 全自动


import ray
from ray.experimental import sandbox

ray.init()

sb = sandbox.create(
    cpu=1.0,
    memory="512Mi",
    image="python:3.12-slim",
    network="none",
)

result = ray.get(sb.exec.remote(
    "python -c 'import sys; print(sys.version)'"
))
print(result.stdout)

sb.delete.remote()

生命周期操作

  • create(image, cpu, memory, network, env, workdir, capabilities, ...)
  • exec(cmd) — 返回 stdout / stderr / exit_code
  • read_file / write_file
  • upload_file / download_file
  • status()
  • delete() / kill()

低层: SandboxRuntime


from ray.experimental.sandbox import SandboxRuntime

@ray.remote
class SandboxPool:
    def __init__(self):
        self.rt = SandboxRuntime()
        self.pool = {}

    def create(self, sid, image):
        self.pool[sid] = self.rt.create(image=image)

    def exec(self, sid, cmd):
        return self.pool[sid].exec(cmd)

单 Actor 内自建沙箱池 → batch 场景省调度开销.

关键: OCI spec 回调


def harden(spec):
    # 防 fork bomb
    spec["process"]["rlimits"].append({
        "type": "RLIMIT_NPROC",
        "hard": 100, "soft": 100
    })
    # 清所有 Linux capability
    spec["process"]["capabilities"] = {
        k: [] for k in (
            "bounding", "effective", "permitted",
            "inheritable", "ambient"
        )
    }
    return spec

sb = sandbox.create(
    image="...",
    _oci_spec_transform_fn=harden,
)

5 · 规模

100,000 gVisor 沙箱
20s 全部启动完成

GKE 实测, 分布在数千节点

为啥能这么快

  1. gVisor 本身亚秒启动
  2. Ray scheduler 把放置决策并行化
  3. Actor 创建不走 kube-scheduler, 直接在 Ray worker 上拉起

对比: 独立沙箱服务通常要过 K8s API server + kube-scheduler, 这规模下 API server 直接压崩.

拆算: 5000 沙箱/秒 总吞吐, 单节点 ~2.5 沙箱/秒 冷启.

6 · 四种网络模式

模式行为典型用途
none (默认)仅 loopback不可信代码执行
public允许出公网装 pip, 调外部 API
host共享节点 netns访问节点本地服务
sandbox独立网络栈沙箱间互通

默认 none = 安全默认. 对 agent 场景, 默认不给网比默认给网安全得多.

文件传输两条路

小文件

  • 配置 / 脚本
  • write_file(path, bytes)
  • read_file(path)
  • 走 Ray object store

大目录

  • 代码仓库 / 数据集
  • tar 打包传输
  • 保留权限 / 符号链接 / 空目录
  • 跨节点自动走 object store

7 · MCP 后端

Ray Sandbox 可作 MCP tool backend. FastMCP 示例:


from fastmcp import FastMCP
from ray.experimental import sandbox

mcp = FastMCP("ray-sandbox")

@mcp.tool
def run_python(code: str) -> str:
    sb = sandbox.create(
        image="python:3.12-slim",
        network="none",
        timeout=30,
    )
    try:
        return ray.get(sb.exec.remote(
            f"python -c {code!r}"
        )).stdout
    finally:
        sb.delete.remote()

安全加固 checklist

  • network="none" 默认
  • capabilities=[] 清所有 cap
  • RLIMIT_NPROC 限制 fork
  • RLIMIT_FSIZE 限制写盘
  • timeout 硬超时
  • CPU / memory 硬限
  • 只读 rootfs (OCI spec 改)
  • 用后即焚 — 不复用沙箱实例

9 · 路线图

  1. REST API 服务 — 训练集群与沙箱集群物理隔离 (PR #65633)
  2. GPU 支持 — kernel generation / RSI 场景
  3. 沙箱内 Docker — gVisor 内跑 docker daemon
  4. 文件系统快照 — 批量 fork 共享 base layer
  5. 跨沙箱端口暴露 — 多 agent 协作
  6. 安全加固指南 — 针对主动尝试逃逸的模型
REST API 这条最关键 — 训练集群通常内网, 跑不可信代码必须隔离域.

10 · 讨论

vs E2B / Modal / Daytona

  • E2B / Modal: SaaS, 独立控制面, 国内不可用
  • Daytona: 开源, Firecracker, 隔离更强但启动慢
  • Ray Sandbox: 跟训练 workload 同控制面, 适合自建 RL 基础设施的团队

为啥不是 Firecracker

Firecracker 隔离更强 (完整 VM), 但:

  • 启动 ~125ms vs gVisor <50ms, 冷启差 2-3 倍
  • 内存开销大 — 每 VM 一份 kernel
  • 10 万并发规模下资源成本不划算
  • 短生命周期 + 高吞吐场景 → gVisor 甜点

攻击面要注意

gVisor 不是银弹.

  • CVE-2023-3978 (DNS 解析) 等历史漏洞存在
  • 共享 host, 侧信道 (Spectre 等) 仍适用
  • 原文明说 "future: guidance for models actively trying to escape"
  • → 官方承认当前防御未针对主动攻击者优化

对 ray-agent 的启发

当前只读诊断, 不涉及. 但若走向:

  • Agent 自动跑诊断脚本 (替代 kubectl exec)
  • 自愈动作执行 (重启 pod 前 dry-run)
  • 用户自带脚本在集群侧跑

Ray Sandbox 是比 kubectl exec 更安全的落点.

短期不动, 长期纳入架构考量.

国内落地建议

  • Ray 2.58 实验性, 生产用观察几个版本
  • 节点需预装 runsc (基础镜像自己打)
  • 国内 GKE 不可用, 自建 K8s + Ray Autoscaler 也能跑
  • 关键看沙箱放置能否复用现有调度策略
